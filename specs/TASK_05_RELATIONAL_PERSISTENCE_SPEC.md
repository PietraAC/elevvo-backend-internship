## 2. Objective

Replace in-memory storage with relational persistence in PostgreSQL through
Prisma ORM and establish the transactional core of an e-commerce backend.

The implementation must demonstrate:

- explicit relational modeling;
- database-enforced integrity;
- versioned and reproducible migrations;
- typed queries with pagination and filters;
- nested relational writes;
- an atomic checkout with complete rollback on failure.

## 3. Expected outcome

The completed API must be able to:

1. persist users and products;
2. maintain one cart per user;
3. relate products to carts and orders through explicit item entities;
4. list products with database pagination and combined filters;
5. convert a cart into an order inside one transaction;
6. prevent partial writes and negative inventory;
7. preserve product name and price snapshots in order history;
8. recreate the database from versioned migrations;
9. prove the main success and rollback paths through automated tests.

## 4. Scope

### 4.1 Included

- PostgreSQL as the primary data store.
- Prisma schema and Prisma Client.
- User, Product, Cart, CartItem, Order, and OrderItem models.
- Essential user and product operations.
- One-to-one, one-to-many, and explicit many-to-many relationships.
- Product pagination and composable filters.
- Nested writes for User + Cart and Order + OrderItem.
- Atomic checkout and stock deduction.
- Logical product deletion.
- Standard persistence error mapping.
- Deterministic development seed data.
- Unit, HTTP, and real PostgreSQL integration tests.
- English documentation and runtime output.
- A reproducible functional demonstration and screenshot guide.

### 4.2 Excluded

- Authentication, password hashing, JWT, and RBAC.
- Redis caching and rate limiting.
- Semantic embeddings and vector search.
- Payment-provider integration.
- Shipping, tax, coupon, and multi-currency calculations.
- Temporary stock reservations.
- Distributed checkout idempotency.
- Order cancellation with stock restoration.
- Physical deletion of orders or historical items.
- A dedicated frontend.

## 5. Mandatory technical decisions

| Decision | Specification | Reason |
|---|---|---|
| Primary database | PostgreSQL | Relational integrity and ACID transactions |
| ORM | Prisma | Typed queries, migrations, and explicit relationships |
| API | Express with TypeScript | Consistency with the internship backend stack |
| Validation | Zod at the HTTP boundary | Safe, testable request contracts |
| Money | `Decimal(12,2)` | Avoid binary floating-point drift |
| Dates | UTC in the database and ISO 8601 in the API | Environment-independent behavior |
| Product removal | Logical deletion | Preserve references and order history |
| Order totals | Calculated by the server | Clients cannot define financial values |
| Order creation | Checkout only | Stock, total, and items are validated together |
| Item history | Product name and price snapshots | Later catalog changes do not alter old orders |
| Checkout isolation | Serializable with bounded retries | Protect stock during concurrent checkouts |

## 6. Domain model

### 6.1 Relationships

| Source | Cardinality | Target | Meaning |
|---|---|---|---|
| User | 1:1 | Cart | Each user owns one active cart |
| User | 1:N | Order | A user may place multiple orders |
| Cart | 1:N | CartItem | A cart contains zero or more items |
| Product | 1:N | CartItem | A product may appear in multiple carts |
| Order | 1:N | OrderItem | An order contains one or more item snapshots |
| Product | 1:N | OrderItem | A product may appear in multiple orders |

The required many-to-many relationships are materialized by `CartItem` and
`OrderItem`. These are explicit entities because the relationships contain
their own attributes, including quantity, unit price, and subtotal.

### 6.2 User

| Field | Logical type | Required | Constraint |
|---|---|---:|---|
| id | Integer | Yes | Auto-incrementing primary key |
| email | Text | Yes | Unique and normalized to lowercase |
| name | Text | Yes | 2 to 120 characters after trimming |
| role | Enum | Yes | `CUSTOMER` or `ADMIN`; defaults to `CUSTOMER` |
| createdAt | Timestamp | Yes | Generated by the database |
| updatedAt | Timestamp | Yes | Updated automatically |

Credentials are outside Task 5. A password field is introduced later with the
Task 10 security requirements.

### 6.3 Product

| Field | Logical type | Required | Constraint |
|---|---|---:|---|
| id | Integer | Yes | Auto-incrementing primary key |
| sku | Text | Yes | Unique, non-empty, and immutable after creation |
| name | Text | Yes | 2 to 160 characters |
| description | Text | Yes | 1 to 5,000 characters |
| category | Text | Yes | Normalized for filtering |
| price | Decimal(12,2) | Yes | Greater than zero |
| stock | Integer | Yes | Greater than or equal to zero |
| active | Boolean | Yes | Defaults to true and controls logical deletion |
| createdAt | Timestamp | Yes | Generated by the database |
| updatedAt | Timestamp | Yes | Updated automatically |

### 6.4 Cart

| Field | Logical type | Required | Constraint |
|---|---|---:|---|
| id | Integer | Yes | Auto-incrementing primary key |
| userId | Integer | Yes | Unique foreign key to User |
| createdAt | Timestamp | Yes | Generated by the database |
| updatedAt | Timestamp | Yes | Updated automatically |

The cart record is reusable. A successful checkout removes its items but keeps
the cart itself.

### 6.5 CartItem

| Field | Logical type | Required | Constraint |
|---|---|---:|---|
| id | Integer | Yes | Auto-incrementing primary key |
| cartId | Integer | Yes | Foreign key to Cart |
| productId | Integer | Yes | Foreign key to Product |
| quantity | Integer | Yes | Positive integer |
| createdAt | Timestamp | Yes | Generated by the database |
| updatedAt | Timestamp | Yes | Updated automatically |

The `(cartId, productId)` pair is unique. Adding the same product again changes
the existing item quantity instead of creating a duplicate row.

### 6.6 Order

| Field | Logical type | Required | Constraint |
|---|---|---:|---|
| id | Integer | Yes | Auto-incrementing primary key |
| userId | Integer | Yes | Foreign key to User |
| status | Enum | Yes | `CONFIRMED` or `CANCELLED`; created as `CONFIRMED` |
| total | Decimal(12,2) | Yes | Positive and calculated by the server |
| createdAt | Timestamp | Yes | Generated by the database |
| updatedAt | Timestamp | Yes | Updated automatically |

### 6.7 OrderItem

| Field | Logical type | Required | Constraint |
|---|---|---:|---|
| id | Integer | Yes | Auto-incrementing primary key |
| orderId | Integer | Yes | Foreign key to Order |
| productId | Integer | Yes | Foreign key to Product |
| productName | Text | Yes | Product-name snapshot at checkout time |
| unitPrice | Decimal(12,2) | Yes | Product-price snapshot at checkout time |
| quantity | Integer | Yes | Positive integer |
| subtotal | Decimal(12,2) | Yes | Server-calculated `unitPrice * quantity` |

The `(orderId, productId)` pair is unique. Historical output must not depend on
the product's current name or price.

## 7. Business rules

### 7.1 Users

- Email is normalized before uniqueness checks.
- Two users cannot share the same normalized email.
- User deletion when orders exist is outside this task.
- Creating a user also creates that user's cart through a nested write.

### 7.2 Products

- SKU cannot be duplicated or changed after creation.
- Price must be positive.
- Stock cannot become negative.
- Inactive products are excluded from the default public listing.
- A product referenced by an order cannot be physically deleted.
- Updating product name or price does not alter an existing `OrderItem`.

### 7.3 Carts

- Each user has exactly one active cart.
- An inactive product cannot be added to a cart.
- Quantity must be a positive integer.
- Removing the final item does not remove the cart.
- A cart item does not reserve inventory.
- Inventory is validated again during checkout.

### 7.4 Orders

- Orders are not created through a generic CRUD route.
- Every order originates from checkout.
- Total is the sum of server-calculated subtotals using prices read inside the
  transaction.
- An order must contain at least one item.
- Confirmed orders are immutable in Task 5.

## 8. HTTP contracts

All endpoints use JSON and the standardized error response in Section 11.

### 8.1 Users

| Method | Route | Behavior | Success |
|---|---|---|---:|
| POST | `/api/users` | Creates a user and nested cart | 201 |
| GET | `/api/users/:id` | Returns a user without sensitive data | 200 |
| GET | `/api/users/:id/orders` | Lists the user's paginated orders | 200 |

### 8.2 Products

| Method | Route | Behavior | Success |
|---|---|---|---:|
| POST | `/api/products` | Creates a product | 201 |
| GET | `/api/products` | Lists active products with pagination and filters | 200 |
| GET | `/api/products/:id` | Returns a product by ID | 200 |
| PATCH | `/api/products/:id` | Updates allowed fields | 200 |
| DELETE | `/api/products/:id` | Performs logical deletion | 204 |

Product-list parameters:

| Parameter | Rule |
|---|---|
| skip | Defaults to 0; minimum 0 |
| take | Defaults to 20; minimum 1; maximum 100 |
| category | Normalized exact match |
| minPrice | Non-negative decimal |
| maxPrice | Non-negative decimal greater than or equal to `minPrice` |
| inStock | When true, only returns products with positive stock |
| active | Defaults to true; administrative use may request false |

The paginated response includes items, `skip`, `take`, and the total number of
records matching the filters.

### 8.3 Cart

| Method | Route | Behavior | Success |
|---|---|---|---:|
| GET | `/api/users/:userId/cart` | Returns the cart and related products | 200 |
| PUT | `/api/users/:userId/cart/items/:productId` | Creates or replaces an item quantity | 200 |
| DELETE | `/api/users/:userId/cart/items/:productId` | Removes an item | 204 |

Task 5 uses an explicit `userId` because authentication has not been implemented
yet. Task 10 replaces it with identity derived from the authenticated token.

### 8.4 Checkout and orders

| Method | Route | Behavior | Success |
|---|---|---|---:|
| POST | `/api/users/:userId/checkout` | Converts a cart into an order transactionally | 201 |
| GET | `/api/orders/:id` | Returns an order with item and user relations | 200 |

Checkout does not accept price, subtotal, or total from the client.

## 9. Checkout transaction

### 9.1 Preconditions

- The user exists.
- The cart exists and contains at least one item.
- Every product exists and is active.
- Every quantity is positive.
- Sufficient stock exists at confirmation time.

### 9.2 Atomic sequence

All steps occur inside the same transaction:

1. reload the cart, its items, and related products;
2. reject an empty cart, missing product, or inactive product;
3. recalculate unit prices, subtotals, and total from database values;
4. deduct each product's stock conditionally, preventing a negative result;
5. create the order;
6. create all `OrderItem` records through a nested write, including snapshots;
7. remove all cart items;
8. commit the transaction.

### 9.3 Failure and rollback

Any failure reverses every transaction change, including deductions that
occurred earlier in the transaction.

Required cases:

- If one item has insufficient stock, no stock changes and no order is created.
- If one `OrderItem` creation fails, the order and every deduction are reverted.
- If cart cleanup fails, the order and every deduction are reverted.
- Concurrent checkouts for limited stock never create negative inventory; only
  purchases supported by available stock may commit.

The implementation uses serializable isolation and conditional stock updates.
Serialization conflicts may be retried a small, bounded number of times and must
never produce an infinite retry loop.

## 10. Persistence and query requirements

- Controllers do not access Prisma directly; they call services.
- Services own business rules and transaction boundaries.
- One shared Prisma client has a controlled lifecycle.
- ID queries load only the required relationships.
- Pagination occurs in PostgreSQL, never in application memory.
- Filters use Prisma `where` clauses and can be combined.
- User + Cart and Order + OrderItem use nested writes.
- Known uniqueness and foreign-key errors map to domain errors.
- Public responses use explicit mappers instead of exposing internal Prisma
  objects directly.

### 10.1 Minimum indexes and constraints

| Entity | Index or constraint |
|---|---|
| User | Unique email |
| Product | Unique SKU |
| Product | Composite `active + category` index |
| Product | Composite `active + stock` index |
| Cart | Unique userId |
| CartItem | Unique cartId + productId |
| Order | Composite userId + createdAt index |
| OrderItem | Unique orderId + productId |

## 11. Error contract

Every error response contains:

- `code`: stable identifier for clients and tests;
- `message`: safe, readable English message;
- `details`: optional validation information;
- `requestId`: correlation identifier when request context is available.

| Situation | HTTP | Code |
|---|---:|---|
| Invalid payload or parameter | 400 | `VALIDATION_ERROR` |
| Missing user, product, or order | 404 | `RESOURCE_NOT_FOUND` |
| Duplicate email or SKU | 409 | `UNIQUE_CONSTRAINT_VIOLATION` |
| Empty cart | 409 | `EMPTY_CART` |
| Inactive product | 409 | `PRODUCT_UNAVAILABLE` |
| Insufficient stock | 409 | `OUT_OF_STOCK` |
| Transaction conflict after retries | 409 | `TRANSACTION_CONFLICT` |
| Database unavailable | 503 | `DATABASE_UNAVAILABLE` |
| Unexpected failure | 500 | `INTERNAL_ERROR` |

PostgreSQL messages, Prisma details, SQL queries, and credentials are never
included in public responses.

## 12. Migrations and demonstration data

### 12.1 Migrations

- The schema is created exclusively through versioned migrations.
- `db push` is not an acceptable final delivery mechanism.
- The initial migration creates enums, tables, keys, relationships, and indexes.
- Database constraints enforce positive price and quantity and non-negative
  stock where Prisma's declarative schema is insufficient.
- Applying every migration to an empty database produces the same final schema.

### 12.2 Seed

The deterministic development seed creates:

- two users;
- six products;
- multiple categories;
- one out-of-stock product;
- one inactive product;
- one cart containing multiple items for checkout demonstration.

The seed first clears Task 5 data in dependency-safe order. It must not run
automatically in production.

## 14. Non-functional requirements

### 14.1 Integrity

- No operation may leave stock below zero.
- No order may exist without items.
- Persisted total equals the sum of persisted subtotals.
- Invalid foreign keys are rejected.
- Failed checkout leaves no partial order, stock deduction, or cart cleanup.

### 14.2 Security

- Input is validated before persistence.
- Client-supplied financial fields are rejected or ignored by contract.
- Secrets never appear in logs or responses.
- Physical deletion of historical order data is prohibited.

### 14.3 Observability

- Database failures are logged with safe operation context.
- Checkout logs success, rollback, duration, and retry attempt.
- Request IDs correlate HTTP requests with transactional logs.
- Sensitive payloads, SQL, and credentials are not logged.

### 14.4 Maintainability

- Routes, controllers, services, mapping, and persistence remain separated.
- Transactional rules are not duplicated in controllers.
- Prisma-generated types do not replace public API contracts.
- Authored content, runtime messages, test names, and documentation are English.

## 15. Acceptance criteria

### AC-01 - Real persistence

After restarting the API and database without deleting the volume, users,
products, carts, and orders remain available.

### AC-02 - Relationships

The API can return a user with orders and an order with products through
`OrderItem`.

### AC-03 - Reproducible migrations

An empty database receives all migrations and becomes application-ready without
manual schema changes.

### AC-04 - Pagination

A list request with `skip` and `take` returns only the requested window and the
total matching the same filters.

### AC-05 - Relational filters

The API can query a user's orders and filter products by category, price,
availability, and active state.

### AC-06 - Nested writes

User creation also creates a cart, and checkout creates the order and related
items without orphan records.

### AC-07 - Atomic checkout

With sufficient stock, checkout creates the order and items, deducts inventory,
and clears the cart.

### AC-08 - Rollback

With insufficient stock for any item, no deduction, order, or partial cart
cleanup remains.

### AC-09 - Concurrency

Simultaneous checkouts never sell more units than available inventory.

### AC-10 - Historical snapshots

Changing a product's name or price after purchase does not modify order-item
snapshots.

### AC-11 - English-only task content

README, documentation, launcher messages, source identifiers, runtime messages,
seed data, and test descriptions are written in English.

### AC-12 - Portfolio evidence

The relational diagram, checkout behavior, rollback behavior, and verification
result can be reproduced using the English demonstration guide.
